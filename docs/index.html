01 — the ideaOne harness, every model

The design follows one metaphor all the way down: the tool shed. The harness is deliberately light — it holds the tools (file access, terminals, web search, vision, MCP servers, infrastructure drivers) and coordinates requests. The model is the engineer who walks in and decides what to pick up. Models are interchangeable; the shed is yours.

🧭

Vodo is the one face

You never juggle providers. Vodo reads what a message actually demands — chat or build, vision, tools, hard reasoning — and hands it to the cheapest model that is genuinely adequate.

🛠

Agents with hands

Agents don't hand you instructions, they do the work: list, read and write files, run commands, search the web, look at images — inside the folder you pointed them at.

🔒

Yours, locally

Keys are encrypted with your OS keychain and go only to providers you configured. Local models (Ollama, LM Studio, llama.cpp) are first-class, not an afterthought.

Group projects

02 — multi-agentEight agents, one goal, one folder

Press Group project, describe the goal, and Vodo plans it: he splits the job into independent briefs, assigns each to the specialist whose routing hints fit, and starts them all at once. You watch every worker in the split view — 4 or 8 panes per page — and you can redirect any of them mid-flight without leaving the screen.

Vodo runs it like a boss, not a bottleneck

  • He delegates the finish. When the parts are in, Vodo hands the assembly to a member instead of doing it himself — he only picks up the tools when nobody else can do the job.
  • Everyone shares one working folder. Members inherit the group's folder, so briefs land as real files next to each other — not as chat text you have to copy out.
  • A stalled member reports to him, not to you. If a worker goes quiet or waits on a permission, Vodo is told and nudges them along.
  • It finishes by itself. Vodo verifies the folder, has the pieces merged, opens the result in Preview and writes the report.

Afterwards it's just chats

  • Every member is an ordinary chat session — archived, distilled, reopenable on its own.
  • The whole run folds into one bundle in the sidebar; delete the bundle and the run's chats go with it.
  • The group shows up in the project's memory map, so a later chat knows what was built and why.
  • Rename anything, any time — chats stay inside their project.

03 — routingCheapest model that's genuinely good enough

Every message is scored for what it really needs, then matched against a live catalogue of models — real provider pricing plus benchmark quality (LMArena Elo, coding-weighted). "Make this look modern" in a project folder wakes a capable executor; "thanks!" costs a fraction of a cent. Each routed reply shows the reasoning and the estimated cost, and per-project meters keep it honest.

Four modes, your rules

  • Auto — cheapest adequate model, per message.
  • My agents first — your specialists get matching work; Auto covers the rest.
  • My agents only — every turn lands on one of your own agents.
  • Off — one model, pinned, forever.

It keeps working when a provider doesn't

  • 429s, 5xx and in-band resource errors back off and retry.
  • A model that keeps failing gets benched and routing moves on without you noticing.
  • A silent or throttled model can't freeze a turn — a stall watchdog aborts it, with a long first-token grace so big prefills aren't killed while they're still thinking.
  • Image requests are never handed to a text model: "generate an image of…" stays on your picked model and renders through your configured image model.

04 — your staffBuild the specialists you actually want

An agent is a name, a system prompt, routing hints, a model (or none, to inherit routing) and the MCP servers it may use. Give a researcher a cheap long-context model and a builder a strong coder; the hints decide who gets which message — and who gets which brief in a group project.

05 — providersNine ways in, one bill you can see

Add a key and the provider's models join the fleet. Flip a provider On/Off without deleting credentials so routing skips it until you want it back. Subscription plans are metered as what they are — a fixed monthly cost, not invented per-token spend.

Local models, taken seriously

  • One endpoint per GPU. Run several Ollama servers and pin a model to a specific box with model@endpoint — the 70B on the big card, the 12B on the small one.
  • Context that fits. Vo-Coder measures what your hardware actually holds and warns before a model spills into system RAM and crawls.
  • Residency control. Keep a model loaded between turns instead of paying the load cost every time.
  • Cache-friendly prompts. The system prefix is stable per conversation, so a local server reuses its KV cache instead of re-reading the whole conversation each turn.

06 — memoryIt remembers, and you can read the memory

Every conversation is kept verbatim in a local SQLite archive and distilled into a structured map — decisions, files, tasks, facts and the links between them — which you can browse and edit. Turn on Smart context and the model's window becomes a buffer over that map: a chat that once replayed 290k tokens a turn drops to a few thousand, with the full record one search away.

  • A journal across everything — chats, projects, missions, tools. Ask "what was I working on last Monday at 10pm?" and the answer comes from the record, not a guess.
  • Per-project memory bank — the map is project-scoped, so every agent in a group sees what the others decided.
  • Searchable archive — agents can pull the exact old exchange back when they need it.
  • Pinned facts survive compaction, restarts and model swaps.

07 — buildingWatch the work happen

Point a chat at any folder — no project needed — and the agent gets tools over it. The Preview tab follows whatever folder the current chat is working in, so you never have to load it by hand.

  • Select code, ask about it — an explanation, a rethink or a change, right where it sits.
  • App preview starts (and stops) your project's dev server, or serves a static page.
  • One-click review runs a real read-only pass, ranks findings by severity, and ends with proposed changes behind Approve / Revise / Don't accept.
  • Permission prompts on every write and command in a chat — you see it before it happens.

A real terminal, and a real starting point

  • PTY terminal with tabs — the same shell your tools run in, right in the window.
  • Scaffolding — an eight-question setup (including target platform: desktop, Android, iOS, website, web app, server) writes a PROJECT_CONFIG.md that agents treat as the project's north star. Beginners get every option explained.
  • Open an existing folder as a project with no questionnaire at all — just tools and memory on that path.

08 — unattendedMissions and a phone in your pocket

A mission is a background objective Vodo pursues in its own isolated agent instance — one-shot or looping on a schedule, concurrent with your chats, so long work never blocks the conversation. Just ask: "check my backups every hour and report problems."

  • Missions run unattended by design — approving the mission is what approves its work, and the prompt that creates one says so plainly.
  • Telegram remote: pair your own bot with a one-time code and talk to Vodo from anywhere — ask questions, launch missions, get run notifications, approve tool calls with inline buttons.
  • Same journal everywhere, so the desktop knows what the phone started.
Optional

09 — infrastructureMr Homelab

Turn him on in Settings and a dedicated infrastructure agent gets his own tab under Terminal — a full chat with voice, Live, folder attach, images and Stop, wired to the bundled infra MCP server.

  • Environment discovery plus a Proxmox driver — VMs, containers, snapshots, backups — behind read < write < destructive permission tiers.
  • A prompt built for the job: read state before touching it, name the blast radius before anything destructive, prefer the smallest reversible step.
  • Out of ordinary routing, so he never absorbs normal chat — but a group project can put him on the infrastructure brief when the goal calls for it.
  • His chats live in his own space and share the same memory as everyone else.
  • The infra server works in any MCP client, not just Vo-Coder. Need more tools? Search the official MCP registry and add servers with one click.

He is an agent like any other

Edit his model, routing hints and MCP servers on the Agents page — he simply comes with the infrastructure prompt and the infra server already mounted.

Nothing happens without you

Destructive infrastructure calls sit behind their own permission tier: a read-only inventory needs no approval, stopping or deleting a VM does.

Off by default

The tab doesn't exist until you tick the box. If you don't run your own metal, you'll never see it.

Free, open source, and installed like any other desktop app. On first run: add one API key — or start a local Ollama / LM Studio server and use no key at all — then say hello to Vodo.

12 — the storyWhy this exists

Vo-Coder is a pet project. I built it for myself and I use it daily — it's shared because it's useful, not because it's finished. There will be bugs; I work through them as they surface. Found one, or want something it doesn't do yet? Discussions is the place.

It's also a port of something bigger. Vo-Coder began as the brain of Vodomation OS — a heavily customized Linux distro with its own desktop environment, currently in the works. There it runs deeper than any desktop app can: most of Vodomation's built-in apps don't need compiling, so Vo-Coder can change and extend every one of them while you use them. Ask the audio app for an effect that doesn't exist and it writes the plugin on the fly. An OS that grows with you.

That framework is so different from a conventional desktop that a straight port was impossible — so this standalone Vo-Coder was rebuilt from scratch to bring the same brain to Windows, macOS and Linux.

Vodo tells that part himself, in his own words, over on Meet Vodo — who he is, how he runs the crew, and what's in the shed.
