01 — the ideaOne harness, every model

The harness holds the tools — files, terminals, web, vision, MCP servers, infrastructure. The model is just the engineer who walks in. Swap models; the shed stays yours.

🧭

Vodo is the one face

You never juggle providers. He reads what a message needs and hands it to the cheapest model that can do it.

🛠

Agents with hands

They read and write files, run commands, search the web and look at images — inside the folder you pointed them at.

🔒

Yours, locally

Keys encrypted by your OS keychain. Local models (Ollama, LM Studio, llama.cpp) are first-class.

02 — multi-agentA whole team, one goal, one folder

Describe a goal. Vodo splits it into briefs, assigns each to the right specialist and starts up to eight at once — the rest queue. You watch every one in split view and can redirect any of them mid-run. No agents built yet? He stands in for them.

  • He delegates the finish. Assembly goes to a member, not to him.
  • One shared folder. Briefs land as real files, not chat text you copy out.
  • A stalled member reports to him, not to you.
  • It finishes by itself — verified, merged, opened in Preview, written up.
  • Every member is an ordinary chat — archived and reopenable.
  • The run folds into one bundle in the sidebar.
  • It shows up in the project's memory, so later chats know what was built.
  • Worktrees mode gives each agent its own git branch instead of one shared checkout — parts merged back once each is built and verified.

03 — pipelinesDraw the team once, keep it

A group project is Vodo planning a crew on the fly. A pipeline is you planning it yourself and saving it. Drop a Foreman, Agent steps and Reviewer gates, then wire them up — pass goes forward, fail loops back.

04 — routingCheapest model that's good enough

Every message is scored, then matched against live provider pricing and benchmark quality. "Make this look modern" wakes a capable executor; "thanks!" costs a fraction of a cent.

Four modes

  • Auto — cheapest adequate model, per message.
  • My agents first — your specialists get matching work.
  • My agents only — every turn lands on one of yours.
  • Off — one model, pinned.

It keeps working when a provider doesn't

  • 429s and 5xx back off and retry; a model that keeps failing gets benched.
  • A silent or throttled model can't freeze a turn — a watchdog aborts it.
  • Image requests never land on a text model.

05 — your staffBuild the specialists you want

An agent is a name, a prompt, routing hints, a model and the MCP servers it may use. The hints decide who gets which message — and which brief in a group.

Local models, taken seriously

  • One endpoint per GPU — pin a model to a box with model@endpoint.
  • Context that fits — you're warned before a model spills into system RAM.
  • Residency control — keep a model loaded between turns.
  • Cache-friendly prompts — the prefix is stable, so the KV cache is reused.

07 — memoryIt remembers, and you can read it

Every conversation is kept verbatim in a local SQLite archive and distilled into a map — decisions, files, tasks, facts and their links. Turn on Smart context and a chat that replayed 290k tokens a turn drops to a few thousand.

  • Two views — Notes lays the map out as editable cards; Graph is the same data in 3D.
  • A journal across everything — chats, projects, missions, tools. "What was I working on last Monday?" is answered from the record.
  • Per-project, so every agent in a group sees what the others decided.
  • Pinned facts survive compaction, restarts and model swaps.

08 — buildingWatch the work happen

Point a chat at any folder — no project needed — and the agent gets tools over it. Preview follows whatever folder the current chat is working in.

  • Select code, ask about it — right where it sits.
  • App preview starts and stops your dev server.
  • One-click review ranks findings, then Approve / Revise / Don't accept.
  • Permission prompts on every write and command.
  • A real PTY terminal with tabs — the same shell your tools run in.
  • Scaffolding writes a PROJECT_CONFIG.md agents treat as the north star.

09 — unattendedMissions, and a phone in your pocket

A mission is a background objective Vodo pursues in its own agent instance — one-shot or on a schedule, so long work never blocks the chat. Just ask: "check my backups every hour."

  • Missions run unattended by design — approving the mission approves its work.
  • Telegram remote — pair your own bot and talk to Vodo from anywhere: launch missions, get notifications, approve tool calls with inline buttons.
  • Same journal everywhere, so the desktop knows what the phone started.
Optional

10 — infrastructureMr Homelab

Turn him on in Settings and a dedicated infrastructure agent gets his own tab, wired to the bundled infra MCP server. Off by default — if you don't run your own metal, you'll never see it.

  • Environment discovery and a Proxmox driver — VMs, containers, snapshots, backups — behind read < write < destructive tiers. A read-only inventory needs no approval; deleting a VM does.
  • Kept out of ordinary routing, but a group project can put him on the infrastructure brief.
  • The infra server works in any MCP client. Need more? Search the official registry and add with one click.

13 — the storyWhy this exists

Vo-Coder is a pet project. I built it for myself and use it daily — it's shared because it's useful, not because it's finished. Bugs happen; I fix them as they surface. Discussions is the place.

It started as the brain of Vodomation OS, a custom Linux distro still in the works. That framework was too different for a straight port, so this standalone version was rebuilt from scratch. Vodo tells that part himself over on Meet Vodo.

License — MIT, one condition

Fork it, ship it commercially, keep your changes closed. The only obligation is a visible "Based on Vo-Coder" credit. Read it →

Privacy

No telemetry, no account, no server of ours in the middle. The only call it makes on its own is the update check — and you can switch that off.
